# 1. CURRENT PRODUCT OVERVIEW
================================================================================

## 1.1 Product summary
----------------------
InboxFlow AI is a multi-tenant SaaS workspace that unifies Gmail and WhatsApp
(and optional Twilio SMS/WhatsApp) into one organization-scoped inbox, runs
single-shot AI extraction into custom tables, syncs structured rows to Google
Sheets, and executes fixed-graph automations (triggers → actions) built on a
React Flow canvas.

It is best described today as:

  Unified Inbox + AI Extraction Pipeline + n8n/Zapier-style Workflow Engine

It is NOT yet a full AI Agent Platform (no planner, tool loop, memory system,
NL→workflow generation, HITL approval, or multi-agent orchestration).

## 1.3 Current architecture & workflow
--------------------------------------
Stack (actual):
  Frontend     : Next.js App Router, React, Tailwind, React Flow
  Backend      : Next.js API routes (Node runtime)
  Database     : PostgreSQL + Prisma
  Auth         : Firebase Auth + Admin session cookies
  AI           : Groq / Gemini / OpenRouter (OpenAI-compatible + Gemini native)
  Channels     : Gmail API, Meta WhatsApp Cloud API, Twilio
  Sheets       : Google Sheets API + Apps Script time-driven sync
  Ops          : Cron routes (CRON_SECRET), webhook logs, Gmail sync locks
  Dev          : ngrok/localtunnel for public URL

Core runtime flow today:

  Event source
    ├─ Gmail sync (manual / cron)
    ├─ WhatsApp webhook
    ├─ Twilio webhook
    ├─ AI task completed
    └─ Cron schedule tick
           │
           ▼
  Persist / update domain data
    (Message, Conversation, AiExtraction, ExtractionTableRow, …)
           │
           ├──────────────────────────────┐
           ▼                              ▼
  Sheet sync pipeline              Automation dispatcher
  (extract missing rows            (match ACTIVE graphs +
   into linked tables →             trigger config filters)
   Apps Script / server push)              │
                                           ▼
                                   Automation executor
                                   (linear DAG of action nodes)
                                           │
                                           ▼
                                   Handlers (send / AI / store /
                                   contact / HTTP)
                                           │
                                           ▼
                                   AutomationExecution + Steps

Important architectural facts:
  - Automations are FIXED GRAPHS. The LLM does not choose tools at runtime.
  - AI calls are SINGLE-SHOT completions with JSON schema validation.
  - Handlers are a hard-coded switch (not a dynamic tool registry).
  - Execution is linear topological order (no condition branches / loops).
  - SCHEDULED_TIME currently fires matching graphs on cron; per-automation
    cronExpression fidelity is incomplete relative to a full scheduler product.

# 2. EXISTING AGENT CAPABILITIES
================================================================================
These features already qualify as building blocks of an AI agent platform,
even though they are not yet composed into a true agent runtime.


## 2.1 Workflow engine
----------------------
  - Visual graph editor (React Flow)
  - Graph JSON stored on Automation.graph
  - Validation: ≥1 trigger, ≥1 action, reachable edges
  - Topological execution order from firing trigger
  - Template context: trigger payload, variables, lastOutput
  - Activate / pause / manual run

This is equivalent to the "workflow graph" layer in n8n / Langflow.


## 2.2 Automations (deterministic agent scripts)
------------------------------------------------
  - Event → match → execute pipeline
  - Per-node step I/O recording
  - Retries with backoff
  - Soft-fail patterns when integrations missing (log / queue instead of crash)

These are "scripted agents" — behavior is predefined by the user graph.


## 2.3 AI extraction (perception / understanding)
-------------------------------------------------
  - Channel-aware prompts (Gmail vs WhatsApp)
  - Structured extraction tasks (lead, order, invoice, sentiment, intent)
  - Custom schema extraction into user-defined columns
  - Auto-reply draft generation
  - Caching by content hash (avoids repeat spend)

This is the "LLM as a skill" layer — not yet an autonomous agent loop.


## 2.4 Event-driven execution
-----------------------------
  - NEW_GMAIL_EMAIL after sync + filter match
  - NEW_WHATSAPP_MESSAGE / NEW_SMS / NEW_TWILIO_WHATSAPP from webhooks
  - AI_EXTRACTION_COMPLETED after successful AI tasks
  - SCHEDULED_TIME via cron
  - Manual dispatch API

This is the "environment → agent wake-up" layer.


## 2.5 Integrations (environment / actuators)
---------------------------------------------
  - Gmail read (sync) + send
  - WhatsApp inbound + outbound
  - Twilio inbound + outbound
  - Google Sheets write path (product pipeline)
  - Outbound HTTP webhook
  - Contacts upsert
  - Key/value store (AutomationDataRecord)

These are the raw capabilities that become TOOLS in an agent framework.


## 2.6 Background jobs
----------------------
  - Gmail sync cron + lock TTL
  - Automation cron + failed execution retry
  - WhatsAppOutboundJob queue processing
  - Webhook idempotency keys / WebhookLog
  - Sheet sync pipeline after Gmail/WhatsApp events
  - Dev tunnel lifecycle for public callbacks

These support long-running / async agent operations.


## 2.7 Tool-like actions (today's handler set)
----------------------------------------------
Already callable as fixed workflow nodes:

  sendEmail          → Gmail API send
  sendWhatsApp       → Meta Cloud API (via outbound jobs)
  sendSms            → Twilio
  sendTwilioWhatsApp → Twilio WhatsApp
  sendMessage        → router across Meta/Twilio options
  callAi             → multi-provider analyze task
  createContact      → Contact upsert
  storeData          → AutomationDataRecord write
  webhookRequest     → outbound HTTP

Missing as first-class tools (exist partially elsewhere):
  gmail.search / gmail.getMessage / gmail.getAttachments
  sheets.read / sheets.insertRow / sheets.updateRow (as automation nodes)
  inbox.search / tables.query / executions.query

# 3. GAP ANALYSIS
================================================================================
Comparison target: modern AI Agent Platforms
(Langflow, n8n AI Agents, OpenAI Agents SDK, CrewAI, AutoGen, LangGraph)


--------------------------------------------------------------------------------
Feature: Natural language → workflow generation
--------------------------------------------------------------------------------
Why important     : Users should describe intent ("When a starred email arrives,
                    extract lead fields, save to sheet, WhatsApp me") and get a
                    draft graph instead of manually wiring nodes.
Business value    : Massive UX leap; demo-friendly; recruiter wow-factor;
                    reduces time-to-first-automation from minutes to seconds.
Technical complexity: High (prompting + schema for graph JSON + validation +
                    repair loop + UI review/edit).


--------------------------------------------------------------------------------
Feature: Agent planner / reasoning loop (ReAct / tool-calling loop)
--------------------------------------------------------------------------------
Why important     : True agents decide which tools to call, observe results,
                    and continue until the goal is met — unlike fixed DAGs.
Business value    : Positions product as Agent Builder, not just Zapier clone;
                    enables ambiguous tasks ("follow up if customer is hot lead").
Technical complexity: High (provider tool schemas, loop limits, safety, state).


--------------------------------------------------------------------------------
Feature: Dynamic tool registry
--------------------------------------------------------------------------------
Why important     : Tools should be discoverable, typed, permissioned, and
                    callable by both fixed workflows AND agent loops.
Business value    : Extensibility; safer integrations; cleaner architecture than
                    a growing switch statement.
Technical complexity: Medium (wrap existing handlers; add JSON schemas;
                    org-level enablement).


--------------------------------------------------------------------------------
Feature: Conditional branching / IF / switch / wait nodes
--------------------------------------------------------------------------------
Why important     : Real workflows need "if lead.confidence > 0.8 then … else …"
                    and wait-for-reply patterns.
Business value    : Unlocks production-grade ops automations.
Technical complexity: Medium (graph model + executor changes + UI).


--------------------------------------------------------------------------------
Feature: Human-in-the-loop (HITL) approval
--------------------------------------------------------------------------------
Why important     : Agents that send customer messages / money-impacting actions
                    need approval gates.
Business value    : Trust, compliance, enterprise readiness.
Technical complexity: Medium (pause execution, notify UI, resume API).


--------------------------------------------------------------------------------
Feature: Agent / workspace memory (short + long term)
--------------------------------------------------------------------------------
Why important     : Agents need conversation context, customer history, and
                    prior decisions — not only the current trigger payload.
Business value    : Better replies, fewer repeated questions, personalization.
Technical complexity: Medium–High (schema + retrieval + prompt injection policy).


--------------------------------------------------------------------------------
Feature: RAG over inbox / tables / sheets
--------------------------------------------------------------------------------
Why important     : "Chat with workspace" and grounded agent answers need
                    retrieval over messages and extracted rows.
Business value    : Differentiator vs generic ChatGPT wrappers.
Technical complexity: High (embeddings, chunking, ACL by org, freshness).


--------------------------------------------------------------------------------
Feature: Chat with workspace (copilot)
--------------------------------------------------------------------------------
Why important     : Natural language interface to inbox, tables, sheets,
                    workflows, and tools.
Business value    : Daily engagement surface; portfolio showcase.
Technical complexity: High (depends on tools + memory + RAG + UI streaming).


--------------------------------------------------------------------------------
Feature: Observability (runs, tools, tokens, cost, latency)
--------------------------------------------------------------------------------
Why important     : Debugging agents without traces is impossible; cost control
                    requires token→$ mapping.
Business value    : Operator trust; portfolio depth; production readiness.
Technical complexity: Medium (extend existing Execution/AiExtraction models + UI).


--------------------------------------------------------------------------------
Feature: Multi-agent orchestration
--------------------------------------------------------------------------------
Why important     : Specialized agents (Email / Extract / Validate / Notify)
                    collaborate with shared memory and handoffs.
Business value    : Advanced architecture story; scales complex processes.
Technical complexity: High (supervisor pattern, shared state, failure contracts).


--------------------------------------------------------------------------------
Feature: Cron expression fidelity + Scheduler product UI
--------------------------------------------------------------------------------
Why important     : SCHEDULED_TIME exists but product scheduler UX is a stub;
                    precise schedules matter for ops.
Business value    : Completes automation story; reduces surprise runs.
Technical complexity: Low–Medium.


--------------------------------------------------------------------------------
Feature: Sheets / Gmail search as first-class automation tools
--------------------------------------------------------------------------------
Why important     : Agents need to READ as well as WRITE the environment.
Business value    : Closes the loop for "check sheet then reply" workflows.
Technical complexity: Medium (APIs mostly exist; need tool wrappers + UI nodes).


--------------------------------------------------------------------------------
Feature: Cost budgets & spend alerts
--------------------------------------------------------------------------------
Why important     : Paid Gemini/Claude usage can spike with backfill + multi-table
                    extract.
Business value    : Prevents bill shock; enterprise hygiene.
Technical complexity: Low–Medium (tokens already stored; need pricing table + UI).

# 5. AI AGENT BUILDER FINAL VISION
================================================================================

Desired end-to-end product flow:


Step 1 — User enters natural language instruction
  Example:
    "When a starred Gmail arrives from a new lead, extract name, phone, budget,
     save to my Leads table and Google Sheet, draft a WhatsApp reply, and wait
     for my approval before sending."

  UI: Agent Builder chat / "Generate workflow" panel on /automations.


Step 2 — AI generates workflow
  System:
    - Loads available triggers, tools, connected integrations for the org
    - Generates Automation.graph JSON (triggers, actions, AGENT nodes, HITL)
    - Runs validateGraph + tool availability checks
    - If invalid, self-repairs once/twice with validator errors


Step 3 — User reviews workflow
  - Graph opens in React Flow builder
  - Diff highlights AI-generated nodes
  - User edits filters, columns, approval policy, messaging channel
  - User clicks Save (draft) or Activate


Step 4 — Workflow saved
  - Persisted as Automation (status ACTIVE or PAUSED)
  - Version snapshot optional (future)
  - Linked tools/permissions recorded


Step 5 — Trigger occurs
  Examples:
    - Gmail sync finds newly starred message matching filters
    - WhatsApp inbound webhook
    - Schedule tick
    - Chat user asks agent to run a playbook
  Dispatcher matches ACTIVE automations + trigger config.


Step 6 — Agent executes
  Two modes coexist:
    A) Deterministic path: classic action DAG (today's executor)
    B) Agent path: AGENT node runs planner loop with goal + tools + memory

  Run creates AutomationExecution + nested AgentRun (new) records.


Step 7 — Tools are called
  Examples during one run:
    inbox.getMessage(messageId)
    ai.extractToTable(tableId, messageId)
    sheets.upsertRow(exportId, values)
    contacts.upsert(...)
    whatsapp.draftMessage(...)   // or send after approval
    storeData.set("leadScore", 0.91)

  Each tool call logged with input/output/latency/tokens/cost.


Step 8 — Memory is updated
  - Short-term: run scratchpad / observations
  - Conversation memory: thread summary for this customer
  - Customer memory: Contact.metadata + CustomerMemory facts
  - Long-term: durable preferences ("always approve WhatsApp sends")


Step 9 — Human approval (if required)
  - HITL node pauses execution (status WAITING_APPROVAL)
  - User notified in app (and optional email)
  - Approve → resume send tool
  - Reject / edit → alternate path or cancel


Step 10 — Results delivered
  - Sheet row written
  - Optional outbound message sent
  - Dashboard / chat receives completion summary


Step 11 — Execution logged
  - Full trace: trigger → agent thoughts (optional) → tool calls → outputs
  - Tokens + estimated USD
  - Errors/retries visible in Observability console
  - Feed used later for self-healing / evals

## 6.9 Recommended tool interface (conceptual)
----------------------------------------------
ToolDefinition {
  name            : string          // e.g. "gmail.sendEmail"
  description     : string
  inputSchema     : JSON Schema
  outputSchema    : JSON Schema
  requiredScopes  : string[]        // integration permissions
  sideEffect      : "read" | "write" | "send"
  requiresApproval: boolean         // default for HITL policy
  execute(ctx, input) → ToolResult
}

Agent loop calls only tools enabled for the org + automation.

# 7. AGENT MEMORY SYSTEM
================================================================================

## 7.1 Memory types
-------------------

1) Short-term memory (run-scoped)
   - Current trigger payload
   - Tool observations for this execution
   - Scratchpad / intermediate variables
   - Maps closely to today's ExecutionContext + AutomationExecution.context

2) Conversation memory (thread-scoped)
   - Per Conversation (Gmail thread / WhatsApp wa_id)
   - Rolling summary + last N messages
   - Updated after each inbound/outbound message and agent run

3) Customer memory (contact-scoped)
   - Durable facts: name, company, preferences, deal stage, open tickets
   - Extends Contact + new CustomerMemoryFact table
   - Used by reply agents and lead scoring

4) Long-term org memory
   - Business preferences ("always use professional tone")
   - Playbook snippets
   - Approved templates
   - Stored as OrgMemoryDocument or namespaced AutomationDataRecord v2


## 7.2 Retrieval strategy
-------------------------
Phase A (ship first — no vectors):
  1. Load trigger message + conversation last N messages
  2. Load Contact by email/phone if present
  3. Load latest ExtractionTableRow(s) for this messageId
  4. Load recent AutomationDataRecord keys used by this automation
  5. Pack into prompt under strict token budget

Phase B (RAG):
  1. Embed Message chunks + ExtractionTableRow text + optional sheet snapshots
  2. Similarity search filtered by organizationId
  3. Re-rank by recency + channel
  4. Cite sources in chat/agent answers


## 7.3 Suggested schema (additive)
----------------------------------
AgentRun {
  id, organizationId, automationExecutionId?
  goal, status, model, inputTokens, outputTokens, estimatedCostUsd
  startedAt, completedAt, errorMessage
}

AgentToolCall {
  id, agentRunId, toolName, input Json, output Json
  status, latencyMs, inputTokens?, outputTokens?, errorMessage
}

  id, organizationId, conversationId
  summary Text, lastMessageAt, tokenEstimate
  updatedAt
}

  id, organizationId, contactId
  key, value, confidence, source  // source: agent|user|extraction
  createdAt, updatedAt
}

  id, organizationId, title, content, kind  // preference|playbook|template
  createdAt, updatedAt
}

MemoryEmbedding (Phase B) {
  id, organizationId
  sourceType  // message|extraction_row|org_doc
  sourceId
  chunkIndex
  content
  embedding   // vector / pgvector
  createdAt

ApprovalRequest {
  id, organizationId, executionId, stepId?
  status  // PENDING|APPROVED|REJECTED|EXPIRED
  summary, payload Json

}


## 7.4 Integration with workflows & agents
------------------------------------------
  - Before AGENT node: assemble MemoryPack (short + conversation + customer)
  - During loop: append observations to short-term; persist AgentToolCall
  - After success: update ConversationMemory summary; write CustomerMemoryFact
    when extraction confidence high; STORE_DATA remains for explicit KV
  - HITL: ApprovalRequest created; memory notes "awaiting approval"

# 10. MULTI-AGENT ARCHITECTURE
================================================================================

## 10.1 Specialist agents (example pipeline)
--------------------------------------------

Email Agent
  Responsibility : Normalize inbound Gmail/WhatsApp/SMS events; classify
                   urgency/intent; fetch thread context.
  Tools          : inbox.getMessage, inbox.searchMessages, gmail.getEmail
  Output         : Canonical EventBrief { messageId, channel, intent, urgency }

Extraction Agent
  Responsibility : Structured field extraction into tables / CRM facts.
  Tools          : ai.extractToTable, ai.analyze, tables.upsertRow,
                   contacts.upsert, memory.set
  Output         : ExtractionResult { values, confidence, tableId }

Validation Agent
  Responsibility : Check required fields, duplicates, policy rules
                   (e.g. phone E.164, budget present).
  Tools          : tables.query, contacts.find, memory.get
  Output         : ValidationReport { ok, issues[], normalizedValues }

Notification Agent
  Responsibility : Notify humans or customers; respect HITL.
  Tools          : whatsapp.sendMessage, gmail.sendEmail, twilio.sendSMS,
                   sheets.upsertRow, approvals.request
  Output         : DeliveryReceipt | ApprovalPending


## 10.2 Communication flow
--------------------------
Supervisor (or linear handoff graph):

  Trigger
    → Email Agent (EventBrief)
    → Extraction Agent (ExtractionResult)
    → Validation Agent
         ├─ ok → Notification Agent
         └─ fail → Notification Agent (ask human) OR stop with error

Handoffs pass a shared RunState object (not free-form chat between agents
in MVP). Each agent writes to AgentRun linked by parentSupervisorRunId.


## 10.3 Shared memory usage
---------------------------
  - Short-term RunState shared across specialists
  - CustomerMemoryFact updated by Extraction/Validation
  - ConversationMemory updated by Email + Notification
  - Org preferences (tone, approval policy) read by Notification


## 10.4 Failure handling
------------------------
  - Per-agent timeout + max tool calls
  - Validation failure → non-retryable unless data changes
  - Send failure → retry with backoff (existing pattern)
  - Supervisor marks parent execution FAILED with failedAgent name
  - Optional compensation: write error row to sheet / notify owner
  - Dead-letter queue for repeated Notification failures


## 10.5 Mapping to current codebase
-----------------------------------
Today's linear automation graph can host this as four AGENT nodes or four
deterministic sections. Multi-agent runtime should sit on top of ToolRegistry
+ MemoryPack — not replace the existing dispatcher for simple Zaps.

## 12.2 Recommended implementation order (highest ROI → lowest)
---------------------------------------------------------------
Order is optimized for: (1) unlock "real agent" claim, (2) reuse existing code,
(3) create demoable portfolio milestones quickly.

  1. Tool Registry + wrap existing handlers
       Why: Foundation for everything; low risk refactor; immediate clarity.

  2. Observability console (runs + tool I/O + tokens)
       Why: Tokens already stored; makes demos debuggable; high credibility.

  3. Token→USD cost + simple budgets
       Why: Low cost, huge production/portfolio signal.

  4. Read tools (inbox.search, tables.query, gmail.getEmail)
       Why: Agents need eyes before brains; data already in Postgres.

  5. Sheets insert/update tools (expose existing write helpers)
       Why: Completes mail/WA → sheet agent story already sold by product.

  6. Agent runtime MVP (single AGENT node, maxSteps, tool loop)
       Why: Core differentiator vs Zapier clone.

  7. HITL approval node
       Why: Makes agent sends safe enough to demo live.

  8. NL → workflow generation
       Why: Best top-of-funnel demo; depends on stable node/tool catalog.

  9. Structured memory v1 (conversation + customer facts)
       Why: Improves agent quality without vector infra.

 10. Chat With Workspace (read-only then confirm-to-act)
       Why: Daily-driver UX; strongest portfolio narrative after agent loop.

 11. Conditional / wait nodes
       Why: Production workflow completeness.

 12. Scheduler UI + cron fidelity
       Why: Closes an existing product gap cheaply.

 13. RAG / embeddings
       Why: Amplifies chat quality once chat exists.

 14. Multi-agent orchestration
       Why: Advanced architecture chapter — after single-agent is solid.

 15. Inbox compose, team invites, billing, marketplace, multimodal
       Why: Important product polish; lower leverage for "Agent Builder" thesis.
